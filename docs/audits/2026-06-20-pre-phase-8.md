## Lens summaries

- **Money integrity** — The happy-path charge ledger is thoughtfully built (immutable rows, derived totals, unique-constraint idempotency, FOR UPDATE on event confirms, amount gates on join/event). But the refund path is effectively broken twice over — refunds never reach the ledger because the metadata it reads doesn't exist on the Charge, and even if it did, it records the CUMULATIVE amount with a mis-targeted idempotency key, producing wrong/double credits. The concurrency safety story is also overstated: transactions run at Postgres' default READ COMMITTED, so concurrent deliveries with different Stripe IDs against the same invoice can lose-update the derived amountPaidCents. Charges are solid; refunds and multi-payment concurrency are not.
- **Forensic security audit** — The auth surface is unusually well-built for a chamber site: HMAC sessions are canonically constructed and constant-time-verified, portal IDOR is correctly closed by deriving identity from the signed cookie (never the body), admin mutations are uniformly gated by requireAdminSession, the Stripe/Resend webhooks verify signatures over the raw body, and SQL is fully parameterized via Drizzle. The real cut corners are in token lifecycle and threshold tuning: portal magic-link tokens are replayable for their full 15-minute window (no single-use enforcement), neither portal nor admin sessions have any server-side revocation (a stolen 30-day portal cookie or 12-hour admin cookie is valid until exp, and rotating CHAT_ADMIN_TOKEN is the only kill switch), and several public write/LLM endpoints rate-limit fail-open. No critical auth-bypass or injection was found, but the session-lifecycle weaknesses are deliberate trade-offs worth surfacing.
- **Data Integrity &amp; Schema Audit** — The journaled schema (0000+0001) is internally consistent with the TypeScript schema — no column-level drift between code and the Drizzle-managed DDL. But the data-integrity story is held together by application-layer convention and two hand-applied off-journal migrations (0002 RLS, 0003 enum) that a fresh `drizzle-kit migrate` will NOT apply and WILL try to duplicate. The denormalized event counters (registrationCount/soldCount/waitlistCount) are increment-only with no decrement path, so any cancellation/refund permanently desyncs them from the real event_registrations rows — a real, accumulating reconciliation gap. RLS is enabled on every table but the app runs as the service role that bypasses it entirely, and there are zero policies, so RLS is security theater unless a separate anon/authenticated path is ever introduced.
- **Forensic correctness + edge-case audit** — The lifecycle code is mostly careful — guarded idempotent UPDATEs, a derived-sum ledger, and string-typed `date` columns compared consistently. But the renewal-engine's headline idempotency claim is false: the 30/7-day notice emails record nothing, so any same-day re-run (cron retry, manual trigger) re-spams every member — the docstring's "double-run won't send duplicates" and "Resend rate limits backstop" are both wrong. Two genuine timezone/leap-year defects exist in join date construction and the UTC-date bridge, plus a few silent-exclusion/intent issues in audience segmentation.
- **Forensic test-quality audit** — The suite is better than average — several genuinely strong tests exist (resend-signature, unsubscribe-token, and the reg-admin suite all use REAL crypto/auth, and the campaign reset test pins the no-double-send guarantee). But the highest-value money-integrity invariant — "a redelivered Stripe webhook never double-charges" — has NO test that runs in the normal green suite: the only real assertion of ledger idempotency/refund recompute is `describe.skipIf(!DATABASE_URL_UNPOOLED)`, skipped in CI, and every other webhook/join test mocks `recordPayment` away. The member-portal auth backbone (`portal-session.ts`) has zero tests and is mocked in every consumer, so a fail-open regression in `verifyPortalSession` would sail through green. Multiple DB-level guards (renewal `WHERE renewalDate=periodStart`, join `WHERE status='pending'`, the FOR UPDATE lock) are asserted only against fake DBs that return canned rows regardless of the predicate, so the predicate itself could be wrong and the tests still pass.
- **Forensic craft + consistency audit** — The core engines are genuinely god-mode, not phoned-in: idempotent campaign claim, guarded-UPDATE-RETURNING webhook counters, the stranded-send reset route's draft-vs-terminal branching, the race-safe expiry sweep, and HMAC unsubscribe tokens are all carefully reasoned and backed by intent-encoding tests. Comments explain WHY, not WHAT. The weakness is consistency hygiene at the edges: the same HTML-escape function is hand-reimplemented four times (a shared escHtml already exists), money formatting is duplicated with divergent decimal rules, a str() validator is copy-pasted into two routes that already import two other validators, and one production email sends from the builder's own huntersystems.dev domain. These are corner-cut chrome on top of a solid frame — none break correctness, but they violate the project's own "match existing patterns / no duplication" rule.

## All findings (deferred items remain open)


### Critical

- `src/app/api/stripe/webhook/route.ts 220-244`
  - Refunds NEVER record in the ledger: the charge.refunded handler attributes via charge.metadata.organizationId/invoiceId, but no code path ever sets metadata on the Charge — only on the PaymentIntent and Checkout Session. PaymentIntent metadata does NOT propagate to the Charge object, so charge.metadata is empty for every charge in this system.
  - **Fix:** Attribute the refund off the PaymentIntent, not the Charge. Read `charge.payment_intent` and either look up the original payment row by `stripeChargeId = charge.id` (then reuse its invoiceId/organizationId), or retrieve the PaymentIntent to read its metadata. The original charge row already carries the correct invoiceId — join to it.
- `src/app/api/stripe/webhook/route.ts 235-243`
  - Even if refund attribution worked, the amount is wrong and the idempotency key is mis-targeted on partial/multiple refunds. `charge.amount_refunded` is the CUMULATIVE total refunded on the charge, but it's recorded as this single event's delta, and the idempotency key is taken from refunds.data[0] which is the MOST-RECENT refund, not the one this event represents.
  - **Fix:** Record the per-refund delta, not the cumulative: locate the specific refund object tied to THIS event (Stripe's charge.refunded does not name it, so subscribe to `refund.created`/`charge.refund.updated` and read `event.data.object` as the Refund, using refund.amount and refund.id). Key idempotency on that refund.id.
- `medina-chamber-site/src/lib/billing/ledger.test.ts 45` _(cut corner)_
  - The ONLY test of real ledger idempotency, the redelivery no-op, and the refund recompute is gated behind `describe.skipIf(!UNPOOLED_URL)` and is skipped in the normal `pnpm test` / CI run. The central money invariant — 'Stripe retries deliveries until 2xx; the UNIQUE constraint on stripeChargeId makes recordPayment a no-op on redelivery rather than a double charge' (route.ts lines 14-19) — therefore has no enforcement in the green suite. A regression that drops the `findExistingByStripeId` fast-path or the unique-violation catch would double-count a payment, flip an unpaid invoice to 'paid', and (via processRenewalPayment/processJoinPayment) wrongly activate a membership — and every check-in CI run would stay green.
  - **Fix:** Add a unit test for recordPayment with a fake DB that simulates the two idempotency paths deterministically: (1) findExistingByStripeId returns a row → assert NO insert happens and idempotentHit=true; (2) the insert throws an object with code '23505' → assert it re-resolves via findExistingByStripeId and does not propagate. Also assert deriveInvoiceStatus is fed the SUM, not the single payment. These don't need Postgres and would actually fail if the guard is removed.
- `medina-chamber-site/src/lib/portal-session.ts 141 (no test file exists)` _(cut corner)_
  - verifyPortalSession is the entire authentication backbone for the member portal (checkout, profile, event registration all gate on it), yet it has NO test file and is mocked in every single consumer test. There is no test that a tampered signature, a wrong-secret signature, an expired token, a missing-dot token, or a forged payload is rejected. A fail-OPEN regression — e.g. `verifyToken` returning the parsed payload before checking `valid`, or swallowing a verify error into a truthy result — would let an attacker forge a session for any organizationId and pay/edit/register as another member, and the entire suite would stay green.
  - **Fix:** Add portal-session.test.ts mirroring resend-signature.test.ts / unsubscribe-token.test.ts: sign a real token with a stubbed PORTAL_AUTH_SECRET, assert round-trip; then assert verifyPortalSession returns null for (a) a body-tampered token, (b) a token signed with a different secret, (c) an exp in the past, (d) a token with no '.', (e) a payload swapped under a valid-but-foreign signature. This is the highest-leverage missing test in the repo.

### High

- `src/lib/billing/ledger.ts 139-204` _(cut corner)_
  - The 'concurrent deliveries are safe' guarantee only holds for the SAME Stripe id (unique constraint). For two DIFFERENT charge ids landing on the same invoice concurrently (legitimate: a dues charge + a manual/event charge, a Stripe retry that minted a new charge, or any split payment), both transactions run at READ COMMITTED (Postgres default — no isolationLevel is ever set), so each SUM(amountCents) misses the other's uncommitted insert and the second UPDATE clobbers the first's amountPaidCents. Derived total under-counts; invoice can wrongly stay 'pending'.
  - **Fix:** Either serialize per-invoice with `SELECT ... FOR UPDATE` on the invoices row at the top of the transaction (forces the second txn to wait and re-read), or run the transaction at SERIALIZABLE/REPEATABLE READ with a retry on serialization failure. FOR UPDATE on the parent invoice is the simplest and matches the pattern already used in confirmEventRegistration.
- `medina-chamber-site/src/app/api/portal/auth/verify/route.ts 25-66` _(cut corner)_
  - Magic-link tokens are replayable for their full 15-minute TTL — they are never marked single-use. The HMAC token is the credential; verifyMagicToken only checks signature + exp, and the verify route mints a 30-day session every time it is presented. portalClaimedAt is set on first login but is never consulted to reject subsequent uses of the same link.
  - **Fix:** Make magic links single-use: store a per-contact magicTokenEpoch (or last-consumed jti) and embed it in the token payload; on verify, reject if it doesn't match, then rotate it so the link can't be reused. Anyone who recovers the link from email forwarding, a proxy log, browser history, or a Referer leak can mint a fresh 30-day session within the window.
- `medina-chamber-site/src/lib/portal-session.ts 141-145` _(cut corner)_
  - Portal sessions (30-day) have no server-side revocation. verifyPortalSession is pure stateless HMAC over { contactId, organizationId, exp } — there is no session-version/epoch column on contacts or organizations, so logout only clears the client cookie. A leaked or stolen portal_session cookie remains valid for up to 30 days with no way to invalidate it short of rotating PORTAL_AUTH_SECRET (which logs out every member at once).
  - **Fix:** Add a sessionEpoch integer to contacts; include it in the session payload and compare on verify. Bump it on logout / suspected compromise to revoke outstanding cookies for that member. Also consider shortening the 30-day TTL.
- `medina-chamber-site/src/lib/db/migrations/meta/_journal.json 4-19` _(cut corner)_
  - Migrations 0002 (RLS) and 0003 (campaign_status enum value) are hand-applied OFF the Drizzle journal. The journal only contains 0000 and 0001. A fresh environment provisioned with `drizzle-kit migrate` (the package.json `db:migrate` script) will apply ONLY 0000+0001 and silently SKIP 0002/0003 — they are not journal entries, so `__drizzle_migrations` never records them and migrate never runs them.
  - **Fix:** Either (a) fold both into proper journaled migrations so `drizzle-kit migrate` is the single source of truth, or (b) add a documented, idempotent post-migrate bootstrap step (a script that runs both .sql files) to the deploy pipeline. Do NOT rely on manual psql for prod cutover. Verify on prod with `SELECT * FROM __drizzle_migrations` vs the actual `relrowsecurity` / enum values.
- `medina-chamber-site/src/app/api/admin/campaigns/[id]/reset/route.ts 91` _(cut corner)_
  - Runtime crash blast radius if 0003 is not applied to prod. The campaign reset route writes status `sent_with_errors`, an enum value that exists in the TS schema and 0003 but NOT in the journaled 0001 snapshot. If prod was provisioned via `drizzle-kit migrate` (which skips 0003), this UPDATE throws `invalid input value for enum campaign_status: "sent_with_errors"` — and this route is "the only way out" of a campaign stranded in `sending`, so the recovery path itself is broken exactly when it's needed.
  - **Fix:** Confirm prod actually has the enum value (`SELECT enum_range(NULL::campaign_status)`) before cutover. Journal the 0003 ADD VALUE so it can never be skipped. Note PG requires ADD VALUE outside a txn on PG<12 — fine on Supabase PG15 but a journaled version must account for drizzle's transaction wrapping.
- `medina-chamber-site/src/app/api/admin/reg/checkin/[id]/route.ts 56-57` _(cut corner)_
  - events.registrationCount / event_tickets.soldCount / events.waitlistCount are INCREMENT-ONLY. They are bumped on confirm (free register route, paid webhook) and on waitlist, but NOTHING ever decrements them. There is no registration-cancellation route, and the check-in route flips status attended<->confirmed without adjusting counts. Any cancelled/refunded/no-show registration leaves the counters permanently inflated vs the real event_registrations rows.
  - **Fix:** Make the counters derived (SELECT count(*) FROM event_registrations WHERE status IN ('confirmed','attended')) for display, or add a cancellation flow that decrements inside the same transaction that changes status. At minimum, run a reconciliation query before cutover and on a cron: `UPDATE events e SET registration_count = (SELECT COALESCE(SUM(quantity),0) FROM event_registrations r WHERE r.event_id=e.id AND r.status IN ('confirmed','attended'))`. Capacity gating (register/route.ts:196) trusts this count, so an inflated count falsely blocks/waitlists real registrants.
- `medina-chamber-site/src/lib/renewal-engine.ts 16-17, 159-228` _(cut corner)_
  - Renewal notice emails (30-day and 7-day) have NO double-send guard within a single calendar day. The file header claims 'Notice emails use exact-day matching so a double-run won't send duplicates' and 'Resend's rate limits also provide a backstop' — both are false.
  - **Fix:** Persist a per-(membership, daysOut, renewalDate) send record (e.g. an email_sends row or a renewal_notices table) and add `AND NOT EXISTS (... already-sent ...)` to the candidate query, mirroring the invoice phase's NOT EXISTS guard. Alternatively make the whole engine resumable so a retry doesn't replay completed phases.
- `medina-chamber-site/src/app/api/stripe/webhook/webhook.test.ts 12-18, 106-138` _(cut corner)_
  - The dues path mock-theaters its own core guard. recordPayment is fully mocked to return `{ invoiceStatus: 'paid' }`, and the test asserts processRenewalPayment runs 'when the invoice is fully paid' — but 'fully paid' is decided entirely by the mock's return value, not by any real amount comparison. There is NO webhook test where a dues PaymentIntent underpays the invoice through the REAL ledger. The amount-underpayment guard for dues lives inside the mocked-away recordPayment/deriveInvoiceStatus, so a regression that recorded a $50 payment as fully settling a $500 invoice (and thus advancing the renewal) would not be caught here.
  - **Fix:** This is acceptable as a routing test IF the ledger's own amount→status derivation is independently covered in the running suite. It is not (see finding #1 — that coverage is skipped). Close the gap by making the ledger idempotency/underpayment unit tests run unconditionally; then this webhook test legitimately only needs to prove routing.
- `medina-chamber-site/src/lib/membership/process-renewal-payment.test.ts 49-54` _(cut corner)_
  - The renewal guard's correctness — the single most important line, `WHERE renewalDate = periodStart AND status IN (active,past_due,lapsed)` which prevents a stale invoice from re-advancing a membership and prevents a cancelled membership from silently reactivating — is never actually exercised. The fake `update().set().where().returning()` returns `advanceRows` regardless of what predicate is passed. The 'idempotent no-op' test simulates the guard by manually setting `advanceRows = []`; it does not verify the guard's WHERE clause is correct. If someone changed the predicate to `eq(renewalDate, periodEnd)` (wrong) or dropped the `status NOT cancelled` filter (the exact bug the source comment warns about — 'a cancelled membership must never silently reactivate'), this test stays green.
  - **Fix:** Either (a) cover this in the staging integration suite with real rows (cancelled membership + paid stale invoice → assert status stays cancelled), making it run in CI; or (b) at minimum assert on the structure of the where() argument so a dropped status-filter or wrong-column predicate trips the test. Right now the test verifies orchestration only and gives false confidence about the guard.
- `medina-chamber-site/src/app/api/portal/checkout/checkout.test.ts 118-160 (missing branch)` _(cut corner)_
  - The `balanceCents <= 0` guard in the checkout route (route.ts lines 92-98) — which refuses to create a Stripe Checkout line item for a fully-paid or overpaid invoice — has NO test. The happy-path test only covers a partially-paid invoice (amountCents 57500, amountPaidCents 7500 → balance 50000). Nothing asserts that a fully-paid invoice (balance 0) or an overpaid invoice (negative balance) returns 400 and never calls Stripe. A regression that removed or inverted that guard would let a member create a $0 or negative-amount Stripe session against an already-settled invoice, and the suite would stay green.
  - **Fix:** Add a test: `invoiceRow = { ...SESSION_ORG, amountCents: 10000, amountPaidCents: 10000 }` → assert status 400 and `sessionsCreate` not called; and an overpaid variant (amountPaidCents 12000) for the negative-balance edge.
- `src/lib/membership/welcome-email.ts 101` _(cut corner)_
  - Production staff-notification email sends from the builder's own dev domain (chamber@huntersystems.dev) instead of the chamber's domain. Every other email in the entire codebase sends from @medinaohchamber.com.
  - **Fix:** Send from a medinaohchamber.com address (e.g. membership@medinaohchamber.com or the env CHAMBER_FROM_EMAIL) so the staff notification isn't sent from an unrelated, unverified domain that can land in spam or fail DMARC.

### Medium

- `src/app/api/stripe/webhook/route.ts 195-216` _(cut corner)_
  - The plain dues path records the charge with NO amount-vs-invoice gate (unlike the join and event paths, which explicitly refuse short payments). It trusts amount_received and relies solely on deriveInvoiceStatus to avoid flipping to 'paid'. A partial/short payment is recorded against the invoice and silently leaves it 'pending' with no alert — and an OVERPAYMENT is recorded as-is, inflating amountPaidCents with no flag.
  - **Fix:** Mirror the event/join discipline: compare amount_received to the invoice's open balance before/after recording, and at minimum log a Sentry warning when a single dues charge != open balance (over or under). The portal checkout sets unit_amount = open balance, so any deviation is an anomaly worth surfacing.
- `src/app/api/events/register/route.ts 242-291` _(cut corner)_
  - Lost-payment window: a paid event registration is inserted as 'pending', then Stripe Checkout is created. If the process dies (or the response is lost) AFTER Stripe Checkout exists but the row is already committed, and the user pays, confirmation works — fine. But if Checkout creation succeeds yet the pending row's amountCents was computed from a ticket whose price/soldCount changed between the SELECT and the insert (no row lock, no re-validation at confirm beyond amountReceived >= reg.amountCents), the seat can be oversold. More concretely: capacity/sold checks (lines 150, 195) are non-transactional reads, and paid seats only increment counts at webhook confirm — so N concurrent paid registrations all pass the capacity check and all later confirm, overselling beyond maxCapacity/maxQuantity.
  - **Fix:** Accepted-risk per the comment, but the paid-ticket gap is larger than 'small' because increments are deferred to the webhook. Consider reserving capacity at pending-insert time (increment a 'reserved' counter atomically) and releasing on checkout-expiry, or enforce maxQuantity with a conditional UPDATE ... WHERE soldCount + qty <= maxQuantity at confirm time.
- `src/app/api/stripe/webhook/route.ts 248-262` _(cut corner)_
  - invoice.payment_failed flips the invoice to 'past_due' via a blind UPDATE keyed on stripeInvoice.metadata.invoiceId, but this app uses one-time Checkout PaymentIntents, not Stripe Invoices, so Stripe-native invoice objects won't carry our invoiceId metadata — and even if they did, this UPDATE can stomp an invoice that was concurrently paid (no status guard). A late/duplicated payment_failed after a payment_intent.succeeded would mark a paid invoice past_due.
  - **Fix:** Guard the transition: `.where(and(eq(invoices.id, invoiceId), inArray(invoices.status, ['pending','draft'])))` so a paid invoice is never reverted, and confirm whether this event type is even reachable in the one-time-charge model.
- `medina-chamber-site/src/lib/admin-session.ts 65-105` _(cut corner)_ — **RESOLVED 2026-06-27+**: dedicated `ADMIN_SESSION_SECRET` (32-char minimum, prod fail-closed) now signs sessions, and per-admin revocation exists via `ADMIN_USERS` + `isCurrentAdmin`. Kept for the record:
  - The admin session is signed with CHAT_ADMIN_TOKEN — the same value that IS the admin password (admin/auth/route.ts compares the submitted password directly to getAdminSecret()). The login password and the HMAC signing key are one secret, so the credential the human types is also the key that forges sessions. There is also no revocation: a stolen 12-hour admin cookie is valid until exp, and the only kill switch is rotating CHAT_ADMIN_TOKEN (which also changes the password).
  - **Fix:** Separate the signing key from the login password (introduce a dedicated ADMIN_SESSION_SECRET, distinct from the human-typed CHAT_ADMIN_TOKEN), mirroring the portal's separate PORTAL_AUTH_SECRET. Optionally add a session epoch for revocation.
- `medina-chamber-site/src/lib/rate-limit.ts 163-252` _(cut corner)_
  - The portal/event public write endpoints (magic-link request, checkout, profile, event registration) all use makeLazyFailOpenLimiter — on any limiter error OR when Upstash env is absent, the request is ALLOWED. limitPortalAuth gates the only email-send-triggering endpoint; a fail-open limiter there means an attacker who can induce limiter errors (or hit an isolate where Upstash init fails) can drive unbounded magic-link emails to any enumerated address and unbounded Stripe-session / DB-write load via event registration.
  - **Fix:** For the auth/email and checkout endpoints, fail closed (or fall back to the in-memory per-isolate limiter like the eager limiters do) rather than fully open. Availability of a guardrail should not mean 'no guardrail' on the endpoints that send mail and create Stripe sessions.
- `medina-chamber-site/src/lib/db/migrations/0002_enable_rls.sql 3` _(cut corner)_
  - RLS is enabled on all 25 tables but the application connects as the Supabase service role (via DATABASE_URL pooler), which BYPASSES RLS, and ZERO policies are defined. RLS here is purely to silence the Supabase advisor — it provides no actual data isolation. If any future code path ever uses the anon/authenticated key (e.g. a client-side Supabase call, a public PostgREST endpoint), every table is locked with no policy = total denial, OR if mis-wired, wide-open. The protection is illusory and the posture is fragile.
  - **Fix:** Document explicitly that data isolation is enforced at the app layer (session cookie -> contactId/organizationId), NOT by RLS, so no future contributor assumes RLS protects the member portal. If the portal ever moves to client-side Supabase access, real policies must be authored first. Otherwise the current setup is acceptable but should be labeled honestly.
- `medina-chamber-site/src/lib/db/schema/memberships.ts 57-58,89` _(cut corner)_
  - Orphaned columns from a half-built recurring-subscription feature. memberships.stripeSubscriptionId, membershipTiers.stripePriceIdAnnual and stripePriceIdMonthly are declared (with a UNIQUE constraint on stripeSubscriptionId) but are NEVER written anywhere in the application. The join flow creates a one-time charge only; activateMembership never sets a subscription id; nothing populates the tier price ids.
  - **Fix:** Acceptable as forward-looking scaffolding IF documented, but flag the risk: the UNIQUE on stripeSubscriptionId is harmless while null (Postgres allows multiple NULLs), and the denormalized organizations.membershipTier (text, also never written by join) can silently disagree with memberships.tierId once subscriptions land. Decide whether Phase 7 will use these or rip them out; don't let them imply a working subscription path at cutover.
- `medina-chamber-site/src/lib/db/schema/events.ts 107-116` _(cut corner)_
  - event_registrations has no integrity constraint guaranteeing a registrant identity. contactId, organizationId, guestName, guestEmail are all individually nullable with no CHECK enforcing (member identity present) OR (guest name+email present). A row with all four null is schema-legal. Identity is enforced only in the register route; any other insert path (import, admin, future code) can create an unattributable registration.
  - **Fix:** Add a CHECK constraint: `(contact_id IS NOT NULL) OR (guest_name IS NOT NULL AND guest_email IS NOT NULL)`. Consider a partial unique index on (event_id, contact_id) WHERE contact_id IS NOT NULL to prevent duplicate member registrations. These are cheap and make bad data impossible regardless of insert path.
- `medina-chamber-site/src/lib/db/schema/events.ts 54` _(cut corner)_
  - Timezone/date-handling fragility at the scrape<->DB join boundary. events.startsAt is `timestamptz NOT NULL`, but db-events.ts matches static-scrape events to DB events by deriving a UTC date string from it, RELYING on the importer having stored startsAt as exactly midnight UTC (date-only). If any event is ever inserted with a real Eastern clock time (e.g. 8:00am ET = 12:00/13:00 UTC, fine) OR midnight ET (which is 04:00/05:00 UTC — same date) it's usually safe, but an evening event stored in ET would shift the UTC date forward a day and SILENTLY break the (title,date) match, dropping on-site registration to the GrowthZone fallback with no error.
  - **Fix:** The join key is a latent bug: any event whose startsAt isn't exactly midnight UTC silently fails to be registerable. Prefer a real shared key (carry the true GZ event id through the scrape AND import instead of synthesizing gzIds), or store an explicit date-only `event_date` column for matching. At minimum add a CHECK or import assertion that startsAt is midnight UTC so a violation fails loud instead of silently un-registering an event.
- `medina-chamber-site/src/lib/membership/join.ts 88-89, 50-52`
  - renewalDate is built with LOCAL-time `new Date(y, m, d)` but then serialized with UTC `toISOString()`. On a server not in UTC this shifts the stored renewal/start date by a day; combined with leap-year normalization a Feb-29 join silently lands on a different date than intended.
  - **Fix:** Construct in UTC for consistency with renewal-engine.ts: `new Date(Date.UTC(y+1, m, d))`, or compute the ISO string directly from UTC parts. This also matches addYears() used elsewhere for periodEnd.
- `medina-chamber-site/src/lib/events/db-events.ts 56-58, 81` _(cut corner)_
  - The (title + date) natural join key silently mis-handles scraped events whose dateISO is empty. events.json contains entries with `"dateISO": ""`, and that empty string is passed straight into the matcher.
  - **Fix:** Early-return null (and optionally warn) when `dateISO` is falsy/not /^\d{4}-\d{2}-\d{2}$/ at the top of getRegisterableEvent, so an unparseable scrape date is an explicit miss rather than an accidental one. Fix the empty dateISO rows in events.json upstream.
- `medina-chamber-site/src/lib/email/audience.ts 48-56`
  - Tier-targeted campaigns silently exclude past_due (in-grace) members. The tier subquery hardcodes membership status = 'active', so a paying member who is temporarily past_due (within the 30-day grace window) is dropped from a tier segment with no signal.
